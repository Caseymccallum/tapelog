## What the M3 inspection showed

The actual M3 browser session linked the earliest error and deny, but its test workflow requested numeric event IDs. A failed call required opening JSON to understand its result, and policy details reduced a call to its last decision. The M3 design had bounded pagination, useful warnings and a cohesive appearance worth extending. The existing engine defines `called` as a recorded result, `attempted` as an observed boundary attempt (answered or not), `sequence` as an ordered subsequence of answered tools, and `denied` as a matching recorded last verdict. These distinctions govern the new UI.

## Delivered

- Select up to 10 calls with keyboard-operable timeline checkboxes, retaining selection across pages and filters. The builder shows selected tools and result availability; users can remove or reorder them. The resulting sequence uses that order, including intentionally different desired ordering. An observed run may fail the requested rule. A recording revision change clears selection and any pending preview.
- The inspector displays the recorded result or error text, recorded time and server, expandable recorded input, linked policy decisions in order, and next investigation steps. Missing results and preview limits are explicitly labelled. Original related and preceding JSON remains available. Readable values reflect the recording's existing redaction; the viewer does not independently redact previously unredacted recordings, which may contain sensitive material.
- The first 20 related events are displayed; linked policy verdict, rule and reason are bounded previews. The comparison adds a separate matched policy-history change summary based on recorded verdict/rule/reason sequences. It does not infer approval actions or forwarding, and retains last-verdict comparison and uncertainty for repeated matching keys.
- The regression builder asks for an explicit desired rule and describes its semantics before preview. It supports the existing denied, attempted, answered, never-answered, zero-attempt, sequence and invariant checks, plus an attempt-count ceiling using the existing `attempted.max_times` engine primitive. The count includes unanswered attempts at this recorded boundary. Tests use the verified reviewed snapshot, do not execute live tools, and require explicit save. Existing save-file protections remain.
- Activity display fields and readable payload previews are bounded; browser lists remain paged, raw details remain on demand, and the comparison limits displayed answered-diff entries. Recorded strings are inserted as text, not HTML. Recording, replay, policy, hash verification, authorization and save implementations were not weakened.

## Known limits and next work

- History comparison pairs by tool/argument hash and occurrence, so duplicate keys and redaction may make matches uncertain. It reports changed histories and counts, rather than a side-by-side diff of every decision. Unassociated events, more than 20 related events and raw results beyond previews need the All events view or original file.
- Result extraction recognizes recorded strings, `message`, and text content blocks; other structured results are displayed as JSON. Previews are capped at 4 KiB, and policy reason previews at 2 KiB. Blob contents are not fetched by the workbench. This display is evidence, not a causal explanation.
- Selecting calls can include unanswered calls, but a sequence assertion rejects them because the existing engine sequences answered calls. Tool-level assertions are not request-specific. `never_called` in the existing engine means no answered result, while zero `attempted` checks observed boundary attempts only; neither proves actions outside Tapelog's view.
- The current schema cannot assert a particular error does not recur. A separate engine proposal should add an explicit negative result/error predicate with clearly defined matching, redaction and missing-result behavior; retain version compatibility, test mutations and seek independent review before exposing it here.
- More work is needed on responsive/keyboard testing with assistive technology, server-side repeated-scan performance, large single metadata fields, richer decision-by-decision comparison, and an independent product/security review. Fixture screenshots are not evidence of all-device usability or real-client integration.
